# 概况：研究脉络与证据

调研日期：2026-10-01。状态：产品设计提案。

## 建议

把“概况”做成论文的研究脉络入口，默认显示**研究演化**，另提供**论点与证据**视图。两种视图来自同一组记录：前者解释研究如何发展，后者解释当前论文的论证结构。普通时间线和主题导图可以作为后续投影。

打开概况时，应能回答四个问题：

1. 当前稿件研究什么，主要主张是什么，适用范围是什么？
2. 最关键的实验或发现是什么，它们支持、限制或挑战哪些主张？
3. 哪些研究方向发生了变化，变化原因和依据是什么？
4. 当前投稿在哪一轮，审稿意见如何影响研究和修订，还有什么具体问题要处理？

核心展示单元是“一个有依据的发现或决定”。一次运行、一次提交、一条会话消息不是天然的关键节点。

## 调研得到的启发

| 方式及参考 | 擅长呈现 | 在本项目中的取舍 |
| --- | --- | --- |
| Obsidian Canvas、Heptabase 白板 | 把笔记、原始材料、主题放在一起，看到关联 | 采用可打开材料的节点、分组和局部展开；自由白板需要持续整理，密集画布不宜成为概况的默认阅读方式 |
| 时间线、带分支的历程树 | 顺序、阶段、并行探索、停止或合并的路线 | 适合默认视图；需要同时显示“变化原因”，避免把先后顺序误当成因果关系 |
| Kialo 的论证映射 | 主张及支持、反对它的理由 | 适合“论点与证据”；科研中还需区分限制适用范围、证据不足和真正的反证 |
| W3C PROV | 一条信息由什么数据、活动和参与者产生 | 采用来源、形成过程、版本的设计思想；不要求引入完整 RDF 标准体系 |
| W3C Web Annotation | 将解释关联到材料的具体片段及当时版本 | 对会话原话、审稿段落、TeX 章节采用定位信息和版本标识，而非只保存文件路径 |

JSON Canvas 的标准节点、边和坐标适合互通及导出，不能单独承担本项目的研究语义：需要额外维护实验引用、决定原因、主张版本和真实发生时间。

## 页面设计

### 顶部：当前论文

用一个简短区域展示当前稿件的研究问题、核心主张、适用范围，以及正在处理的具体事项。例如：“固定预算下的模块收益依赖数据条件；修订稿正在补充多种子评估。”每个信息可点开对应稿件、实验或修订记录。

保留会话、写作、实验、投稿的轻量入口。把当前以文件路径为主体的大卡片让给研究内容。研究资料不足时展示真实可得的信息；没有数据的贡献、结论和任务不生成占位项。

### 默认视图：研究演化

主体按时间由早到晚连接关键节点，读起来像有分支的研究故事：

> 提出问题 → 尝试方法 → 发现关键结果 → 调整研究主张 → 形成稿件 → 投稿与审稿 → 修改或转投。

这只是常见阅读路径，不能强迫每篇论文填满这些阶段。并行路线、回到旧问题、停止探索都应能表达。

节点常态只展示标题、一句关键内容、真实时间与少量来源标记。转折节点直接写“原来的想法 → 新的想法”，并露出一句有来源的原因。例如：

> 停止继续堆叠模块，转向解释适用条件。
>
> 原因：同预算对照未观察到稳定额外收益，研究备忘明确决定收缩这条路线。

未观察到收益不等于证明模块无效。原实验条件和不确定性在详情中保留。

停止的路线保留为淡色分支，说明停止原因；当前路线保持清晰。多次运行归入相应实验，普通文稿提交归入版本阶段。初始视图保留重要发现、影响决定的负面结果和投稿节点，按需展开其他内容。

“重要”首先来自用户固定、稿件实际引用、已记录的研究决定、关键评审意见与当前待解决问题。AI 可以建议加入主线，不能因为结果不显著或路线失败而把它们藏掉。

### 第二视图：论点与证据

从当前稿件的一条主张出发，显示相关研究问题、支持实验、限制条件、反例或挑战、审稿意见以及相应修订。

边要有语义：“检验”“支持”“限定”“挑战”“促成调整”“回应”“写入稿件”“提交版本”。同一实验可以关联多个主张；同一条审稿意见可能引出多个修改。只展开当前选择的主张及相邻关系，避免默认显示整个项目的所有连线。

此视图用于回答“这句话依据什么”“这条意见改了哪里”“哪些结论已收缩”，而不是展示运行统计或抽象的完成度。

### 点击节点：详情与来源

右侧详情随选择变化，窄窗口改为下方展开。按内容显示：当时的问题、得到的发现或做出的决定、变化前后、原因、适用条件、关联材料和后续处理。

来源必须可直接定位：实验 ID 与概览版本、运行记录、投稿事件与审稿原文、`.paper/` 提交及章节、会话中的具体消息。概况的短文可以由 AI 整理，原始审稿文字、评分、结果文件和原始思考记录保持原貌。

打开来源需要在相应页面定位到记录，不只切换到“实验”或“投稿”首页。来源失效时保留引用及当时的摘录，明确指出找不到哪份材料。

## 现有数据与缺口

| 数据 | 已具备 | 需要补充 |
| --- | --- | --- |
| 论文项目 | `Paper` 有题目、简介、路线、旧版本及修改任务 | 简介不等于稿件主张；旧路线主要保留创建时间，缺少方向变化历史 |
| 实验 | 分组、实验概览、概览修订、运行、来源运行 ID；组可关联 `routeId` | 实验与稿件主张、审稿意见之间的关系；区分实验结论与作者做出的研究决定 |
| 文稿 | `.paper/` 文件、内部 Git 版本、差异 | 关键章节和主张的定位；版本形成原因；将已提交版本与当前工作稿分开读取 |
| 投稿 | 投稿链、事件、审稿原文、来源、稿件标签或 Git 提交 | 审稿意见到研究决定、实验及修订版本的显式关联 |
| Agent 会话 | 目录对应的会话索引、标题、首段预览和更新时间 | 项目范围内的历史消息只读接口、消息时间和片段定位；当前预览不足以复原完整思考过程 |
| 思考与决定 | 可能分散在会话、笔记、提交说明中 | 一个低成本的“记录思考”入口，保存作者的真实问题、判断和转向原因 |

当前 `PaperOverview` 主要提供导航和路径，尚未合并实验、投稿及 Git 历史。Codex 的 `thread/read` 目前用于核验所属目录，未向界面提供消息正文；Claude 的扫描也主要提取会话元数据。因此首次整理能建立事实历程及现有文稿主张，但不能承诺恢复所有历史研究决策。

## 整理与更新方式

### 首次整理

1. 程序收集项目范围内的实验、概览修订、投稿事件、文稿版本，形成带稳定 ID 和版本标识的事实目录。
2. Agent 按任务读取当前稿件及关键历史差异、实验结论、审稿原文、用户笔记；相关会话正文需要补齐只读接口后再接入。
3. 提取有出处的研究问题、主张、发现、决定和关系。每条事实关联材料及具体位置。不能仅根据“时间相近”推断某次拒稿导致某个新实验。
4. 对没有明确原因的变化，保留可以证实的先后关系。AI 推测可以在详情里作为解释建议，不能自动成为已确认的因果边。
5. 保存整理结果，并允许用户修改标题、摘要、主线选择或关联关系。人工修改在后续整理中保留。

不要求用户先维护一张白板。可以用现有默认 Agent 与权限设置启动“整理研究脉络”，之后沿用这个项目的整理会话补充信息。

### 记录思考

一个文本输入即可记录：“我决定停止方案 A，因为同预算实验没有稳定提升，后面改查条件 B。”也可粘贴会话片段、文件、图片或链接，让同一 Agent 提取并关联。

这段作者原话本身是决定的来源。需要记过去的事情时可补发生日期；日期不明就保持不明。不同于实验结果，这里允许保存问题、计划和个人判断，避免把未完成计划写成已经得到的研究发现。

### 后续更新

文件索引发现新增运行、正式概览变化、关键稿件版本或投稿进展后，记录变更范围。用户发起整理时只读取变更及相关上下文；本地事实索引可以自动更新，不必每次文件保存都调用 AI。

变更落到同一来源对应的稳定节点上。一个主张真的发生变化时保留前一版本与取代关系；AI 只是换了摘要措辞不应新增一个历史里程碑。人工备注、固定节点及人工关系覆盖应独立保存，重整时合并。

## 数据设计与实现建议

沿用已有本地存储与 CLI 写入模式，拟在 `.repaper/overview/` 保存研究整理结果、人工记录及修订。原始实验、稿件、投稿仍通过其各自接口读取。

图由两类节点组成：

- 既有事实的投影：实验概览、运行证据、Git 版本、投稿与审稿事件，引用既有 ID，不重复保存一份可编辑业务记录。
- 新增语义记录：研究问题、假设或主张、发现、决定、思考原文。记录摘要、适用范围、来源、真实发生时间、录入时间以及替代关系。

关系保存起点、终点、关系类型、关系的依据和整理者。来源定位可采用：记录 ID、概览或事件修订号、Git commit、文件路径与哈希、章节 label、消息 ID、原文摘录及上下文。行号只用来辅助导航，文件改动后不能继续冒充旧证据。

查询和发布接口可考虑以下**拟新增**入口：

```text
repaper overview context --json
repaper overview show --json
repaper overview publish --file <draft.json>
```

发布需保留来源版本、稳定 ID、历史修订和人工编辑，并采用原子写入与修订冲突检查。实际 CLI 名称可在实现时确定。配套 `repaper-overview` Skill 负责整理，并加入初始化生成的 `AGENTS.md`；现有三个 Skill 继续承担各自职责。

界面默认的时间树可先用 React 与 SVG 连接线实现。局部证据图若需要成熟的缩放、选择和键盘操作，可采用 React Flow；布局交给 Dagre 或 ELK，而非自行开发通用布局引擎。React Flow 本身不提供自动布局。ELK 更适合多父节点及复杂连线，代价是配置和异步布局处理；简单有向结构用 Dagre 更轻。

当前项目没有 React Flow 或 ELK 依赖。应先验证内容结构是否有用，再决定是否引入画布引擎；缩放和节点拖拽不能代替内容整理。

## 建议的第一版

第一版形成一个完整但有限的使用闭环：

1. 合并已有事实目录，展示当前稿件、关键实验、投稿与文稿版本。
2. 支持记录思考和一次 Agent 整理，形成有来源的决定与转折。
3. 用同一模型展示研究演化和局部论点关系，节点可以进入真实来源页面。
4. 增量整理保留人工修改，并区分计划、已发生事实及有范围的研究结论。

随后再扩展完整会话提取、更深的历史比较、回溯某一稿件版本的研究状态，以及 JSON Canvas 导出。第一版不需要依靠把所有历史会话都读完才能产生价值。

## 评价标准

- 用户能从转折节点找到当时改变方向的原因与材料。
- 用户能从一条稿件主张找到相关支持证据、限制条件和评审挑战。
- 用户能从审稿意见找到回应它的实验、决定或修订；尚未关联的意见保持可见。
- 增加一次重复运行不会产生一堆挤占主线的节点。
- 保留不成功的路线和旧主张，回看时不把今天的理解套到过去。
- 原始评分与审稿意见不被概况摘要替代。
